# Project: ИИ‑агент для фиксации договоренностей в телефонных разговорах

Кроссплатформенное мобильное приложение для пользователей и их менеджера.
Пользователь принимает или совершает звонки через приложение (VoIP/PSTN через
Voice Provider). После consent‑flow разговор записывается и анализируется ИИ:
выделяются договоренности, сроки, обязательства и следующие шаги. Пользователь
подтверждает результат, после чего создаются задачи, напоминания и события
календаря. Менеджер видит задачи своей команды на общей доске и аналитику.

Источник требований: `plan.md`. При расхождении между этим файлом и `plan.md`
остановись и спроси, не угадывай.

## Product rules

- Продукт фиксирует договоренности: обязательства, сроки, встречи, платежи,
  обещания, follow‑up и открытые вопросы.
- Никогда не создавай задачу, напоминание, событие календаря, заметку,
  сообщение клиенту или запись во внешней системе без явного подтверждения
  пользователя.
- Каждая извлеченная договоренность обязана содержать:
  - type
  - title / object
  - owner: user, counterparty или unknown
  - due date (и время, если применимо)
  - source quote из транскрипта
  - audio start/end timestamps
  - confidence
  - status
- Статусы договоренности: `detected`, `requires_review`, `needs_clarification`,
  `confirmed`, `rejected`. Задача создается только из `confirmed`.
- Если confidence ниже порога (по умолчанию 0.8), статус `requires_review`,
  задача автоматически не создается. Порог хранится в конфигурации.
- Если информация неоднозначна (срок «на следующей неделе», нет суммы, неясен
  ответственный), ставь `needs_clarification`. Не выдумывай даты, суммы, имена
  и обязательства.
- Сохраняй оригинальную цитату и аудио‑таймкоды для аудита.
- Пользователь может отредактировать или отклонить любое предложенное действие.
- Автоматическая отправка сообщений клиенту запрещена. Только черновик, который
  пользователь отправляет сам.
- Статусы задач: `new`, `in_progress`, `done`, `overdue`, `canceled`.

## Роли и доступ

- Две роли: `user` и `manager`. Админ‑панель и сложная ролевая модель вне MVP.
- Пользователь видит только свои звонки, договоренности, задачи и напоминания.
- Менеджер видит задачи всех пользователей своей команды (`team_id`) и
  аналитику. Задачи других команд недоступны никогда.
- Проверка прав выполняется на сервере, а не только в UI. Каждый endpoint
  менеджера проверяет роль и принадлежность к команде.
- Менеджер видит задачи и метаданные, но доступ к аудио и транскриптам
  подчиненных не получает, пока это не решено отдельно и не записано в `plan.md`.

## Consent flow (критично)

- Запись начинается только после состояния `answered` и успешного consent‑flow.
  Это правило нельзя обходить ни в коде, ни в тестах, ни в демо‑режиме.
- Жизненный цикл звонка:
  `incoming → ringing → answered → consent_notice → consent_result → recording →
  analyzing → in_progress → completed`, плюс терминальные `missed` и `failed`.
  Переходы валидируются в domain‑слое конечным автоматом, недопустимый переход
  это ошибка.
- Логика backend на `call.answered`:
  1. проверить согласие пользователя приложения;
  2. нет согласия → обычный звонок, запись не включается;
  3. проиграть собеседнику аудио‑уведомление;
  4. зафиксировать consent‑событие;
  5. собеседник отказался → запись не включается;
  6. согласие получено → запустить запись и media stream;
  7. запустить ASR и ИИ‑анализ;
  8. отправить в приложение событие `analysis_started`.
- Режимы согласия собеседника: уведомление + продолжение разговора, активное
  согласие (DTMF 1), отказ (DTMF 2), предварительное согласие (SMS/app link).
- В таблице `consents` фиксируй версию текста согласия, дату, метод
  (`app_settings`, `audio_notice`, `dtmf`, `sms_link`), `call_id` и статус
  (`granted`, `denied`, `withdrawn`).
- Пользователь может отозвать согласие и запросить удаление данных. Реализуй
  это как сценарий, а не как «потом».
- При отсутствии согласия приложение продолжает работать как обычный звонок и
  показывает ручной ввод договоренностей.

## Architecture rules

- Mobile client: Flutter/Dart в `apps/mobile` (стек из плана: Flutter, один
  кодовый бейз для iOS и Android).
- Backend и ML pipeline: Python/FastAPI в `services/api`.
- Не размещай бизнес‑логику, ML‑инференс и адаптеры внешних систем в виджетах
  Flutter.
- Чистое разделение слоев:
  - UI: виджеты и состояние
  - Application: use cases и state controllers
  - Domain: сущности и бизнес‑правила
  - Infrastructure: API‑клиенты, локальная БД, нативные интеграции
- Слои backend:
  - `api/`: HTTP‑роуты, WebSocket, схемы запросов и ответов
  - `domain/`: сущности, enums, конечные автоматы, правила валидации
  - `services/`: Call Session, Consent, Agreement, Task, Notification,
    Manager Dashboard
  - `ml/`: VAD, diarization, ASR, LLM‑извлечение
  - `integrations/`: Voice Provider, календарь, напоминания, уведомления
  - `workers/`: асинхронные задачи (ASR, AI, notifications)
- Внешние системы подключаются через общий порт/интерфейс:
  - `VoiceProviderPort` (answer, hangup, play_notice, start_recording,
    open_media_stream)
  - `CalendarPort.create_event()` / генерация `.ics`
  - `RemindersPort.create_reminder()`
  - `MessagingPort.send_summary()` (только после подтверждения)
- Новый провайдер или интеграция добавляется адаптером, без изменений в ML
  pipeline и мобильном UI. Voice Provider выбирается на этапе 1, до этого
  используй порт и mock.
- Серверная PostgreSQL единственный источник истины. Локальная БД на телефоне
  это кэш и очередь офлайн‑изменений, а не отдельная система учета.

## Cross-platform rules

- Android и iOS из одной кодовой базы Flutter.
- Никогда не используй Android‑only или iOS‑only API в feature‑коде.
- Платформенный код (CallKit/PushKit на iOS, Telecom/ConnectionService на
  Android, APNs, FCM, фоновый режим) прячь за абстрактным интерфейсом и
  внедряй реализацию через DI.
- Запрашивай разрешения только при использовании функции: микрофон,
  уведомления, календарь, контакты, фоновая работа.
- Предусмотри fallback при отказе в разрешении: ручной ввод, share sheet,
  локальный черновик.
- Не считай, что поведение календаря, напоминаний и входящих VoIP‑звонков
  одинаково на обеих платформах. Тестируй оба пути.
- В backend используй UTC, часовой пояс пользователя храни отдельно.
- Все даты в UI форматируй по локали устройства.
- Мобильное приложение не контейнеризируется. Docker только для серверной части.
- Вне MVP: запись обычных сотовых звонков в системном приложении «Телефон».
  Не пытайся ее реализовать.

## Звонки

- Входящий: Voice Provider → push → приложение → «Ответить» → `Call.answer()` →
  consent → запись → media stream → ASR + LLM.
- Исходящий: приложение → VoIP → Voice Provider → PSTN → обычный номер.
  Собеседнику приложение не нужно, ИИ‑фиксация работает на стороне инициатора.
- Обрабатывай события: входящий, гудки, ответ, завершение, обрыв, пропущенный.
- Потеря сети во время звонка не должна терять уже записанное. Покрой это
  тестами (Wi‑Fi, 4G, слабый сигнал).

## ML and data rules

- Обработка аудио асинхронная: загрузка или старт возвращает conversation/call ID
  и статус обработки, а не блокирующий результат.
- Порядок пайплайна:
  media stream → decoder → VAD/chunking → diarization → ASR → transcript buffer →
  LLM extraction → validation → Agreement Service → WebSocket → пользователь
  подтверждает → задача/напоминание/событие.
- Храни отдельно: сырой вывод LLM, провалидированный результат и правки
  пользователя.
- Не доверяй дате из LLM без проверки относительно даты разговора и часового
  пояса пользователя («до пятницы» разрешается детерминированно в коде).
- Транскрипт хранится в таблице `transcripts`. Не дублируй его в `calls`.
- Повторная обработка аудио должна быть идемпотентной.
- Аудио и транскрипты содержат персональные и коммерческие данные: шифруй,
  ограничивай доступ, задавай ограниченный срок хранения аудио.
- Промпты и ответы LLM логируй только с редактированием (redaction) и согласия
  пользователя.

## API и WebSocket

- Каждый endpoint имеет схемы запроса/ответа (Pydantic v2) и обработку ошибок.
- Эндпоинты из плана: `/auth/login`, `/calls`, `/sync`, `/me/tasks`,
  `/tasks/{id}` (PATCH), `/tasks/{id}/complete`, `/manager/team/tasks`,
  `/manager/team/stats`, `/manager/team/members`.
- События WebSocket: `partial_transcript`, `agreement_detected`,
  `analysis_started`, `call_ended`. Схема событий версионируется, и после
  изменения обновляется OpenAPI и генерируется API‑клиент.
- Access token JWT с коротким сроком жизни и refresh token.

## Локальная БД и синхронизация

- Локальная SQLite хранит только данные пользователя: профиль и роль, его
  задачи и договоренности, последние звонки, офлайн‑черновики, outbox,
  `sync_token`, версии записей.
- Не хранить: задачи других сотрудников, данные команды, лишние аудиозаписи,
  данные без права доступа.
- Поток: UI → Repository → Local DB → Outbox → Sync Engine → Server.
- Цикл: pull (`GET /sync?since=`) → применить к локальной БД → push outbox →
  ack и удаление успешных операций → обновить `sync_token`.
- Каждая операция имеет `idempotency_key`. При ошибке retry с backoff. При
  конфликте сервер возвращает авторитетную версию (поле `version`).
- Синхронизируются дельты, не вся база. Локальный кэш всегда можно
  восстановить с сервера.

## Код и данные: безопасность

- Аудит: `audit_log` фиксирует согласие, старт записи, изменения договоренностей
  и задач.
- Не коммить секреты, ключи API, аудиофайлы и реальные транскрипты.
- Значения в `docker-compose.yml` для Postgres/MinIO (`app`, `minio123`) только
  для локальной разработки. Реальные значения идут через `.env`, в репозитории
  только `.env.example`.

## Code quality

- Dart: строгие настройки analyzer, иммутабельные модели, Riverpod для
  состояния, никакой бизнес‑логики в виджетах.
- Python: ruff, mypy, Pydantic v2, dependency injection, async I/O.
- Каждая внешняя интеграция должна мокаться в тестах (в том числе Voice
  Provider и LLM).
- Пиши тесты до изменения логики извлечения, валидации, расписаний, consent,
  синхронизации и интеграций.
- Обязательные тесты: переходы состояний звонка, блокировка записи без согласия,
  разрешение относительных дат, порог confidence, права доступа
  менеджера/пользователя, идемпотентность sync.

## Docker и контейнеры (только сервер)

- Каждый компонент работает в своем контейнере: `api`, `worker-asr`, `worker-ai`,
  `worker-notifications`, `postgres`, `redis`, `minio`, `nginx`. Все они в одной
  сети docker compose. Серверная часть MVP поднимается командой
  `docker compose up -d`.
- Контейнеры обращаются друг к другу по имени сервиса (`postgres`, `redis`,
  `minio`), никогда не по `localhost` или `127.0.0.1`. Внутри контейнера
  `localhost` это сам контейнер.
- Адреса и учетные данные задаются только переменными окружения
  (`DATABASE_URL`, `REDIS_URL`, `S3_ENDPOINT` и т. п.). Хосты не хардкодятся.
  При запуске на хосте (тесты, отладка) те же переменные указывают на
  `localhost` и опубликованные порты.
- Наружу публикуется только `nginx`. `postgres`, `redis` и `minio` в
  production не публикуют порты. В dev их открывает
  `docker-compose.override.yml`.
- У `postgres`, `redis` и `minio` есть healthcheck. Сервисы, которые от них
  зависят, используют `depends_on` с `condition: service_healthy`, а не просто
  порядок запуска.
- Миграции (Alembic) выполняет отдельный одноразовый сервис `migrate`: он
  стартует после `postgres` и до `api` и воркеров. Не запускай миграции при
  старте API и не запускай их из нескольких контейнеров одновременно.
- Контейнеры stateless. Данные живут только в named volumes (`postgres_data`,
  `redis_data`, `minio_data`) и в S3‑хранилище. Аудио и транскрипты не пишутся
  в файловую систему контейнера.
- Не выполняй `docker compose down -v` и не удаляй volumes без явного
  разрешения пользователя: это уничтожает данные.
- `api` и воркеры используют общий код и общий образ с разными командами
  запуска. Воркеры общаются с API только через очередь и БД, не по HTTP.
  ML‑тяжелые зависимости выноси в отдельный build target воркеров, чтобы образ
  API оставался легким.
- Интеграционные тесты запускаются против контейнеров. Юнит‑тесты не требуют
  Docker.
- Мобильное приложение не контейнеризируется. URL бэкенда задается
  конфигурацией сборки, не хардкодом: эмулятор Android → `10.0.2.2`,
  iOS simulator → `localhost`, физическое устройство → IP хоста в локальной
  сети или HTTPS‑домен.
- `nginx` терминирует TLS и проксирует WebSocket (заголовки `Upgrade` и
  `Connection`, увеличенные таймауты).

## Порядок работы

Следуй этапам из `plan.md` и не перескакивай:

1. Подготовка: MVP‑сценарий, роли, стек, Voice Provider, структура репозитория.
2. Серверная основа: Postgres, Redis, storage, модели, auth и роли, CRUD,
   Docker Compose.
3. Мобильная основа: авторизация, контакты, личная доска, локальная БД,
   Repository и sync.
4. Звонки: Voice SDK, входящие VoIP, исходящие на обычные номера, экран звонка.
5. Consent flow: экран согласия, уведомление собеседнику, фиксация, блокировка
   записи без согласия.
6. Запись и анализ: media stream, streaming ASR, LLM, события по WebSocket.
7. Договоренности и задачи: live‑карточка, редактирование и подтверждение,
   задачи, напоминания.
8. Доски: личная и менеджера, фильтры, сортировка, аналитика, ограничение
   доступа.
9. Итог звонка и календарь: резюме, черновик сообщения клиенту, событие
   календаря или `.ics`, история звонков.
10. Тестирование и демо.

Перед началом этапа кратко проверь, что предыдущий выполнен и тесты зеленые.
Работай небольшими шагами: схема и тесты, затем реализация, затем документация.

## Вне MVP

- Запись обычных сотовых звонков в системном «Телефоне».
- Интеграция с корпоративной CRM.
- Многоязычный ASR (в MVP язык `ru`).
- Сложная ролевая модель и админ‑панель.
- Автоматическая отправка сообщений клиенту без подтверждения.
- Биллинг, тарифы и корпоративный SSO.

## Definition of done

- Функция работает на Android и iOS или имеет явно описанное платформенное
  ограничение.
- Запись невозможна без `answered` и consent. Любая внешняя запись требует
  подтверждения пользователя.
- Тесты покрывают доменные правила, контракт API и адаптер интеграции.
- Права доступа проверены на сервере для обеих ролей.
- Нет секретов и персональных данных в коммитах.
- Документация обновлена, если изменились API, модель данных или пользовательский
  сценарий.
- Критерий MVP: демо проходит от входящего звонка до задачи на доске менеджера
  менее чем за 3 минуты.

## Python dependency management

- Используй `uv` для всего Python‑кода в `services/`.
- Не создавай и не редактируй `requirements.txt` для backend.
- Не редактируй `uv.lock` вручную.
- Runtime‑зависимости: `uv add <package>`.
- Dev‑зависимости: `uv add --dev <package>`.
- Запускай инструменты через `uv run` (`uv run pytest`, `uv run ruff check .`,
  `uv run mypy .`).
- Коммить `pyproject.toml` и `uv.lock`, не коммить `.venv/`.
- После изменения зависимостей выполни `uv sync` и убедись, что тесты проходят.
- Тяжелые ML‑зависимости держи в optional dependency group, если они не нужны
  для локального запуска API.
